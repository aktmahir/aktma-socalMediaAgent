## Remaining work

### Provider verification

The adapters now use current request patterns and have mock tests for response parsing, authentication headers, and failure fallback. Credentialed smoke tests are still needed to verify provider-side permissions, model availability, and live response shapes.

### Web test coverage

The form performs basic validation and displays status feedback. Flask test-client coverage includes valid generation/scheduling, invalid schedule input, upload size boundaries, signature/media-type checks, unique storage names, rejected uploads, and single-user authentication/session flows.

### Durable scheduling

Scheduling writes files through local process workers and persists job records, attempts, and generated outputs in SQLite. CLI lifecycle controls, manual recovery, an opt-in local supervisor, a Docker Compose supervisor, per-job worker leases, and bounded generator retries are available. Windows users can opt in to current-user logon startup with `scripts/register-scheduler-supervisor.ps1`; no Windows task is registered automatically.

### Media workflow

Uploads are limited to 5 MB, validated against allowlisted extensions, basic signatures, and selected media type, and stored using random server-generated names. Image/video parsing is bounded; optional ClamAV may be unavailable, and semantic vision is sent to OpenAI only after explicit user opt-in. This does not constitute exhaustive parsing or a safety guarantee.

### Production operation

The app supports local development and single-user local/Docker operation. The default Compose sample remains loopback-only HTTP; an optional Nginx TLS overlay provides local TLS termination, redirects HTTP to HTTPS, and removes the app's host-published HTTP port. Compose also runs a separate scheduler supervisor sharing the app's SQLite database/output volume, with leases coordinating active workers and recovering abandoned jobs. The stack is not a complete public production deployment: external certificate issuance/renewal, firewall/reverse-proxy deployment policy, dedicated secret management, Sentry project setup, alert notification routing, and broader monitoring remain. Forwarded headers are ignored by default; deployments must configure the exact trusted proxy-hop count and peer IP and prevent untrusted direct access to the app. Local log file rotation and Docker stdout/stderr retention are configurable. Web schedule paths are confined to `SCHEDULED_OUTPUT_ROOT` (default `scheduled_posts`). Readiness is available at `/ready` and requires TLS-ready cookie settings. The local development limiter defaults to process-local storage; the Docker configuration uses Redis.
